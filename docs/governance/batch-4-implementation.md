# Governance batch 4: native expansion branches and rule hierarchy observations

This follows ADR v1.2 and #79 without registering production code paths,
applications, policies, writers, executors or schema patches. Four project axes
remain native; optional features stay off. No deployment or production
permission migration is performed.

## N05

An explicitly attached, identity-matched native Wiki content object permits
observation of the actual existing-document batch expansion prelude. The
observer records editor-local old-content context, ordered deletion/move-policy
expansions and project milestone context. Task/Wiki policy pass-through branches
are local native expansion observations, not native validation or risk closure.
Maniphest full batch, support expansion, Herald and final effects remain blocked.

## N07

The fixed rule catalog calls actual native Users, any-project, all-project and
project-member rule methods in the verified owned SELECT-only context. Actual
ProjectQuery provides parent/ancestor/member attachments; structural checks
refuse inconsistent parent references, paths, keys or depths rather than
silently truncating the chain. Unknown/missing sources are distinct from a
known local rule deny. Inverse and materialized membership semantics remain
native, including their differences; this does not add membership inheritance.

An empty all-project list may produce native local true; it is not complete
policy authorization. Policy composition, action/order, ruleHasEffect and all
runtime dependencies are not certified. The source capture and subsequent
native queries use different connections/read views: they are not one atomic
authorization observation or a business-write lock. Post-query row/depth limits
do not prove full SQL time/memory bounds under concurrent source growth.
These gaps are explicit unknowns. Every result remains partial and non-executable.

## Validation gates

The required native workflow retains previous fixtures and adds a separate
batch-4 artifact. Source-derived native DDL and synthetic rows, actual SQL
privileges, owned cleanup and configuration/cache isolation remain mandatory.
New literal member consumers are explicitly reviewed without weakening either
inventory scanner. Complete caller/source closure, native rule composition,
whole transaction effects, execution atomicity and unproven resource budgets
remain activation blockers even when selected observations pass.

## Development validation

Supported PHP 8.5.12 / MySQL 8.4.13 in an owned network-none pod passed 87 pure
native methods, the prior 85 native-source SQL checks and 51 new native rule/
expansion SQL checks. All 32 executed governance PHP/SQL/map/runner files matched
the source worktree. Governance Python has 31 tests; the permission suite has
82, including explicit review of the new read-only member consumer. The fixture
removed all eight owned schemas and its SELECT-only reader.

Actual execution corrected two test assumptions: native Lisk depths may be
canonical decimal strings; native project-group rules use materialized-edge
queries and do not automatically inherit the separate milestone member-attachment
semantics. The runtime semantics are preserved. The shared Wiki content fixture
uses the actual native WRDS PHID type, and the old 85 checks were rerun.

These are source-copy development receipts, not release or production evidence.
Final-head independent review, required PR CI and post-merge main verification
must be recorded separately. Local counts alone do not authorize activation.
