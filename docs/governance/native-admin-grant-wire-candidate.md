# Native administrator grant wire fixture candidate

This successor adds an isolated native-producer fixture, not a production change. Its source baseline is `e5f89aac566b121f2ebb3894aa4ba76b31222c10`. The verified e5 full profile and earlier organization wire profiles remain historical evidence; they do not prove this new fixture or native administrator SMTP delivery.

The dedicated `--notice-admin-grant-wire-hold` path starts with a normal approved non-administrator and a verified primary address. A separate existing native administrator, loaded through a real synthetic web session and CSRF request, grants the role with `PhabricatorUserTransactionEditor`. The fixture reads the actual saved USER transaction, requires its real author, and derives the immutable notice identity from that row. A distinct same-primary observer must see the committed role, USER transaction PHID and event together. Real native no-effect replay must leave one transaction and event. No fixture appends an outbox event directly, assigns a producer class to a fabricated mail, or calls mail preparation/authorization to manufacture a passing result.

The only candidate cases are `allow` and `admin-revoked`. Exactly one current qualified administrator has a verified primary destination. The private ready record identifies a native-admin-grant source. The separate fixed CLI control binds that actual USER transaction PHID, subject, operator session and event; it has no caller-selected target or public mutation route. Revocation uses the real native editor, session and CSRF, verifies a true-to-false USER transaction, and confirms committed role removal from another primary connection. It does not prepare or authorize a mail during mutation.

The physical parent still needs a separate signed-source implementation and review. Its positive case must run actual Notice, Prepare and Submit daemons from the pinned Gorge revision, the native HTTP callback, and stable Owlmail v0.14.0; it must observe exactly one generic link-only MIME message and no replay duplicate. Its negative case must prepare the actual immutable snapshot first, revoke the role, then exercise the actual per-physical native callback and require denial, durable quarantine and zero SMTP. A direct mailer physical execution in the negative case must not be called a negative Submit-daemon proof.

Production source, resources, schema, native permission axes and default-off settings are unchanged. New classes and PHP pure methods are not added; source-derived declarations remain 261 methods in 43 classes, and the normal 934-check profile is unchanged. No supported-runtime, SQL, physical callback, SMTP, all-producer, OFF-to-ON activation, deployment, or new recipient-class proof is claimed by host contracts or this candidate document.
