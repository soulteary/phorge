## Family assignment and coverage boundary

The primary readset belongs to `file-capabilities`: native File rows and their attachment/transform dependencies. The author automatic-capability branch also informs `object-automatic`. One evidence package may be referenced by both families; it must not be counted twice or mark either family complete. Author PHID is only this slice's bounded selection root. It does not enumerate all files a subject can see through arbitrary objects, possession of secret URIs, or every automatic-capability object type.

The actual File automatic function grants an author the function result before considering its capability argument. For nonauthors, the VIEW branch uses already attached objects or an already attached original. It is FileQuery, not this function, which loads those objects using the viewer and the ANY-visible-associated-object rule. A model with pre-attached objects is a function test, never ordinary-viewer authorization proof. Disabling the author does not change the low-level function; account/session admission is separate and unchanged.

Only `attach` rows become FileQuery policy attachments. `reference` is not a grant and native detach removes the row via the generic transaction Editor. A reference update preserves an existing attachment. Attachment's own extended policy delegates to its parent object. No direct fixture SQL write will stand in for these native transitions.

Transforms may have multiple real sources due to deduplication. Current FileQuery ignores VOID as a grant, preserves real sources, and selects a deterministic visible original; a VOID entry cannot hide a real source. Standalone profile/builtin shortcuts are distinct from derived profile behavior. `isBuiltin()` reads the metadata builtin name, not `builtinKey`. This prototype deliberately does not load metadata or interpret profile/builtin or transform providers. It returns that boundary as false, never an inferred authorization decision.

## Prototype readset

The code uses the actual cached native User writer under the existing explicitly owned RR scope, verifies the scope before and after its reads, and accepts only a strict isolated namespace. A planned User PHID is rechecked under a PRIMARY shared current read. It then opens all three File source tables before observing table/index/column metadata; those observations are not a proven grant or DDL lease.

The real tables are `file`, `file_attachment` and `file_transformedfile`. File's unique index is `phid`, not `key_phid`; its author index is `authorPHID(authorPHID)`. Attachments use `key_file(filePHID)` and unique `key_object(objectPHID,filePHID)`. Transform indexes are unique `originalPHID(originalPHID,transform)` and nonunique `transformedPHID(transformedPHID)`. The prototype checks exact engine/index uniqueness, full nonprefix sequences, scalar types, bounded lengths and nullability before loading facts.

The File author range is bounded to 64 files. Per-selected-file attachment and incoming/outgoing transform ranges are read in deterministic order, with an explicit 128-row cap for each individual query and a global 256-relation/64 KiB primitive binding budget. Each query fetches a 129th sentinel and rejects it before merging; the aggregate row budget is checked after every batch before issuing another query. A 129-row result must never be accepted as a complete 128-row range. An empty author range is still queried, but no phantom exclusion is claimed before actual independent-producer tests. Unknown attachment parent types outside the explicitly limited Task fixture reject. Transform names are opaque bounded data; no dynamic provider is instantiated. Observed cycles reject; external transform and parent-object frontiers remain incomplete.

No metadata LONGTEXT, secretKey, mailKey, storageHandle, or file bytes are loaded by this collector. Thus the code does not claim to bind secret download capabilities, profile/builtin semantics, or full File policy. A later metadata slice must first lock/index-plan IDs and byte lengths, enforce aggregate budgets, then load bounded PRIMARY payloads and recheck identities and sizes. It must not add LONGTEXT to this SELECT before that mechanism exists.

Only fully validated scalar arrays reach HMAC serialization. The binding key is fresh and private, summaries contain fixed fields only, and finishing is single use even after failure. The native RR scope remains a prototype: its API quarantine is not DAO-cache eviction, and unknown physical outcomes need disposable-worker/independent cleanup. This source does not make that architecture production-adoptable.

## Native producers and staged development

1. File creation is actual `newFromFileData` through the already owned, pinned Gorge file service. The unregistered fixture preparation reuses real account/avatar preparation before enabling recovery/RR, creates an ordinary author's File, reloads it, and creates an actual Task with that ordinary author. Any native create/view/edit refusal remains a failed prerequisite.
2. Attachment transitions use actual Task transaction Editor `TYPE_FILE` and native modes. The Editor validates that the acting user can load each File. Explicit and implicit remarkup attachments, the direct `attachToObject` upsert and parent deletion/destruction are separate producer paths; one successful Editor path does not cover the others.
3. Transform generation uses actual `executeTransformExplicit`, which records a relation only for a nonbuiltin source and a nontransient result. Cache lookup, controller regeneration/destruction, deduplicated multiple sources, VOID/builtin records, and raw DAO/SQL writers require separate coverage. No fake row should be called a native transform producer.
4. File policy edits can scramble file secrets, including attached files when a parent policy changes. FileDataController separately validates per-file secret knowledge, optionally with MediaFileGuard. The adapter does not read or export those secrets; full restoration safety for these consumers remains blocked.
5. File deletion affects inbound/outbound transforms, attachment destruction and optional Gorge deletion outbox/storage. Cleanup must prove actual process/storage/session ownership and must not assume that a Task transaction and the separate File application connection share one physical transaction. Independent observers must establish commit and rollback behavior on each relevant native writer.

Registration and additive N00 are prepared on stable current main: 165 sources/162 links/127 runtime files remain explicitly partial. Native unit registration, portable exact method IDs and typed consumer are source-reviewed candidates only; supported map and SQL require independent gates. The Atomic step is prepared after Task30, preserving its source-bound references and success-only five-member artifact. It has not run. The prepared profile is designed to distinguish ordinary-user FileQuery deny/allow from direct function behavior, real native producer success/refusal, rollback of attachment/history/storage side effects, independent raw INSERT/UPDATE/DELETE waits/reaps across both RR terminal outcomes, transform frontiers, actual schema/privilege/DDL negatives, and exhaustive owned cleanup.
