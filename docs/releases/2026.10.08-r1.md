## 发布与部署方式

Gorge 当前流程只推送候选镜像，通过十四项服务的打包检查和独立配对交付验收后，
在 GitHub Release 发布 `release-manifest.json`。它不再生成新的 `service-<CalVer>`
或晋升 `service-latest`，不能把 `GORGE_IMAGE_TAG` 改为 `2026.10.08-r1` 来部署本版。

基础 Compose 保留 `2026.10.07-r2` 的历史默认值，仅适用于这些标签实际存在且
已经完成对应源码配对验收的旧栈。部署当前版时，按 manifest 的 Phorge/Gorge
提交检出源码，为全部启用的服务以 `image: ghcr.io/soulteary/gorge@sha256:...`
逐项覆盖。具体步骤见 [发布镜像与源码配对](../../DOCKER.md#发布镜像与源码配对)
和 [Gorge 发布门禁](https://github.com/soulteary/gorge/blob/d0b8703abee84cb614fbe585b914ee08d3eca002/deploy/release/README.md)。

运行时滚动升级先更新 Phorge PHP consumer，再更新 Gorge db-api。新版 PHP 能兼容
读取 1.1，但旧 PHP 不识别 db-api 1.2 新增的复制状态标签；这项部署顺序与先发布
Gorge 镜像产物的发布顺序分开处理，见 [db-api](https://github.com/soulteary/gorge/blob/d0b8703abee84cb614fbe585b914ee08d3eca002/docs/modules/dbapi.md)。

## 发布顺序

1. 完成并合并两仓库的 `2026.10.08-r1` 发布准备 PR，记录最终 Phorge/Gorge `main` 提交。
2. 将 Gorge 的 `PHORGE_CONTRACT_REF` 与 Phorge 的 `GORGE_CONTRACT_REF` 设置为这两个最终不可变提交，重新运行配对契约与交付检查，核对产物中的源码身份。
3. 将 Gorge `2026.10.08-r1` 标签指向已验证提交，触发 Release；工作流使用固定 Phorge 配对提交构建十四项候选镜像并进行隔离验收。
4. 等待 Gorge Release 全部成功，核对 manifest 中的版本、两个源码提交、服务 digest 与验收结果，再在已验证的 Phorge 提交创建 `2026.10.08-r1` 标签和 Release，记录同一配对身份。
5. 以 manifest digest override 部署；生产邮件供应商、认证后浏览器流程、真实数据恢复和容量指标仍按部署文档单独验收。

PR 检查和源码契约成功不等于镜像已经发布。不要沿用旧版“先生成同版本服务标签，
再升级公共标签”的顺序，也不要将不同运行的候选 digest 混为一套发布产物。

所有 Compose 验证显式使用空环境文件，不读取安装自己的 `.env`，不启动生产
服务。本地 PHP 8.5 检查只覆盖上述范围；完整配对 Docker 基线仍为 PHP 8.3。

发布 PR 的常规检查验证配对源码契约及其声明的真实依赖，不能等同完整 Docker
交付验收。Gorge Release 工作流另外必跑完整配对 Docker 交付：检查十四项候选
镜像的打包身份，并将当前 image/render 候选 digest 用作实际业务 fixture；其他
服务的完整候选运行覆盖以 [发布门禁](https://github.com/soulteary/gorge/blob/d0b8703abee84cb614fbe585b914ee08d3eca002/deploy/release/README.md) 为准。
本地静态配置检查不替代这些结果，也不证明邮件真实送达。
