# Selected native OAuth access-token owner compatibility

This candidate starts from main fc0369af9d84c4a5f23a7080528e70f1ce84c4e7. OAuthServer and its access-token schema are retained native sources. Existing NativeCaptureScope already reads OAuth API sources; this increment adds cooperative native access-token INSERT serialization and bounded observation by a borrowed current User writer. It does not enable OAuthServer or account recovery.

The actual OAuthServer generateAccessToken() still creates and saves the native access-token DAO. With recovery disabled, the original parent INSERT runs unchanged. With recovery enabled, the existing selected producer fence resolves the independent native User and OAuth writers, refuses forced connections and unowned outer transactions, acquires each table's shared metadata lock inside its own owned READ COMMITTED transaction, checks InnoDB, and holds the User PRIMARY shared lock through native OAuth INSERT and OAuth commit. User cleanup follows OAuth commit. These are two transactions, not a distributed atomic transaction. Unknown commit or cleanup retains process-local quarantine; PHP process exit cannot guarantee a live lease survives.

Borrowed observation uses the actual registered Store owner and observer lifecycle. It never begins, commits, rolls back, closes or changes the owner's isolation. It verifies native OAuth routing and same primary, takes OAuth metadata lock and checks ENGINE on the current User owner, and reads at most 64 subject rows with fixed columns and byte budgets. Missing SELECT permission fails closed; no grant is added. Repeated capture and owner-end validation require the same digest. A caught source error poisons the participant. This RC observation is separate from Task/File owned repeatable-read consumers.

The 7 Python tests run actual core and Store methods with explicit SQL collaborators, and actual native OAuth factory/DAO methods with native isolated connections and database network functions disabled. They are host source/behavior evidence, not physical SQL, metadata-lock, DDL, wait or unknown-commit evidence. Existing Conduit SQL6 covers selected borrowed-owner commit/rollback obligations; it does not prove its DDL or unknown-commit fault matrix and cannot establish this OAuth candidate.

Root-run physical fixtures remain required: native OAuth producer blocked by the borrowed User PRIMARY lock for both owner commit and rollback; new owner-event binding after actual INSERT; setup-principal DDL blocked by each transaction's metadata lock; foreign/RR/raw outer transactions refused without ending caller transactions; and actual unknown OAuth commit/User cleanup retained without false cleanup proof. No fixed callable OAuth SQL phase is wired yet.

Authorization codes, client authorizations, client policy changes, external OAuth credentials, raw SQL and noncooperative INSERT/UPDATE/DELETE producers remain outside this selected hook. A User shared lock cannot prevent those writers or general phantoms. The API family and all 13 recovery families remain incomplete. Production observer factory, durable review/submit integration, execution authorization and restoration permit remain unavailable/false.
