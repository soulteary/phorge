# Isolated real native Project-description SQL qualification

This recipe is executable orchestration, not a SQL success report. Nothing here
activates production features, publishes images, deploys or migrates online data.
The tracked description entry and early fixture template both retain null Root
profile pins and refuse before native initialization when invoked directly.

## Fixed lifecycle

1. Verify committed recipe files and an exact reviewed metadata-recipe lock, the
   current source admission, target `577ae2eb82d854753b88f2985a154e409272068a`
   / tree `f4d5435523b65587f54465b9c5712ad0b0d8f8f8`, actual loopback-only
   disposable MySQL 8.4.13 image and PHP 8.5.12 with CLI OPcache/JIT disabled.
2. Reuse the real metadata recipe's fresh owned namespace, standard native base
   upgrades and two native admin accounts/tokens plus ordinary recipient and
   direct business-team membership. The baseline source is actual
   `4c2245300dc1d78d042b95190dd537eb6b1f9861`, not the description runtime.
3. An explicit boolean-only `description_fixture` extension runs after baseline
   readback and **before target configuration enables isolated flags**. Its
   SHA-bound fixed template, copied with only one profile-pin substitution,
   creates a new synthetic Project through actual native name/view/edit
   transactions. The ordinary recipient must actually have VIEW and lack EDIT.
   It does not edit any existing protected object or change flags to avoid a
   guard. The original metadata target/profile shape is unchanged.
4. Standard target migration and original metadata grant/revoke readbacks run
   unchanged on T3. Read the private early-fixture receipt and bind a new profile
   to its distinct Project, namespace, exact source files, database receipt,
   current configuration and genuine administrator actors.
5. Copy the explicitly reviewed diagnostic successor PHP entry and byte-exact
   raw-v2 cases into an owner-only private
   helper directory. Replace only its single `null` profile constant with the
   SHA256 of this newly created exclusive private profile. Original tracked files retain null pins. `cases.php` and its nine business
   cases remain byte-exact; the entry adds bounded diagnostics without changing
   profile admission or business guards. The runtime source pin binds actual T3
   entry bytes, while the separately reviewed private diagnostic template is
   bound to current recipe bytes and its full template hash.
6. Execute all nine real cases through T3's native source/editor: no grant,
   user success, trigger-induced use-audit rollback, direct unsealed transaction
   refusal, revoked grant, direct-team success, expiry, deleted credential and
   disabled account. Reobserve database identity and current source afterward.
   A private child journal retains original outputs and known/unknown terminals.

The dedicated workflow only uploads the allowlisted success summary; it never
uploads credentials, actor tokens, profiles, journals, target PHIDs or namespaces.
All failures produce bounded phase labels with SQL status **unknown**, retain
private evidence and never retry or perform speculative cleanup. Successful
namespaces are explicitly retained too: `cleanup_executed=false`. Destruction of
the disposable CI service at job teardown is an infrastructure responsibility,
not proof of in-recipe namespace cleanup.

## Current blocked integration

This isolated package was authored against signed local T3 before the separate
source-admission successor was frozen. `metadata-lock.json` intentionally binds
only the existing predecessor recipe; it cannot admit the pending combined
source. `load_shared` additionally requires the exact T3 target/tree, so the old
T2 recipe is refused. This is a real gate, not a warning that execution ignores.
Root must compose the independently reviewed early-fixture diff with the actual
source-admission package and refresh its exact shared helper/template pins,
complete metadata inverse/descriptor and this recipe lock from the **actual
combined bytes**. No future SHA, arbitrary caller lock or null/empty bypass is
accepted. A committed current recipe, available T3 object and full current-source
admission must pass before the workflow can execute SQL.

Host tests cover profile-pin construction, unchanged default metadata behavior,
strict boolean selection, direct null-pin refusal and detached receipt scope
validation. Detached vectors and query capture are not successful SQL evidence.
The target SQL run remains unexecuted here. Exact schema upgrade, genuine current
credentials, actual ordinary VIEW/noEDIT success, audit rollback and all nine
native outcomes must still be observed by Root in the isolated runtime.

Publish-task/mail/feed **intent** is the current boundary. No worker delivery,
Herald completion, browser, HTTP, CSRF/MFA or full N05 production acceptance is
claimed. Postcommit publication failure cannot mean an already committed body
and use-audit were rolled back. Those Q2 effects remain separate gates.

## Failure diagnostic successor

The PHP entry now emits exactly a fixed refusal marker and one safe JSON line.
It projects a closed phase/family enum, a fixed query-errno alias or null, and at
most four allowlisted source-alias/line locations. Unknown sources are `other/0`;
messages, exception names, arguments, SQL, tokens, IDs and absolute paths are never
projected. The old one-line-stderr expectation intentionally fails against this
successor and its updated test validates the stricter two-line contract.

The parent publishes this projection only after the exact invocation ordinal,
private intent argv, started PID and known nonzero terminal match, no unknown
record exists, stdout is empty and stderr validates in full. Duplicate keys,
extra fields, warnings, mixed raw stderr, unbounded locations and unknown
terminals produce no public native diagnostic. There is no fallback to another
ordinal or observer-selected file and no retry. Private journal bytes remain
retained. Detached tests of these checks never certify real SQL execution.
