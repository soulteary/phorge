# Optional compound approval workbench candidate

Base: signed PR119 source `8b1de3e77d487e6b7f13c684f76f0ae527d76831`. This source-only candidate adds `/people/organization/approvals/` to the existing People application. The existing `governance.organization.enabled` option stays locked and false by default. It introduces no role, policy migration, schema migration, backfill, permission-axis change, automatic dispatcher or recovery permit.

A current native system administrator can discover and open compound membership/appointment requests, review the original impact, and use the existing independent-approval and bound-executor services. The directory's existing proposal forms remain the proposal interface; their confirmation now links directly to the new record. This does not reimplement transfer/handover or introduce a new approval mechanism.

## Discovery and private data

The actual approval schema has a binary opaque-ID primary key and no state/time index. Pages therefore show recorded requests in ID order, never “latest requests” or an exhaustive pending-work count. The UI has explicit record links and next-page navigation. A bounded page can contain no compound requests while still providing its next cursor.

Before any binding body is loaded, the adapter reads and validates bounded primary-index metadata: IDs, lengths of both binding columns, participant index version/PHIDs and row version. The limit is 25 records plus one metadata sentinel. Each non-null binding has the existing 32 KiB bound. The aggregate body plan is at most 32 × 32 KiB (1 MiB) and 32 distinct participant PHIDs. Repeated participants count once. A byte/participant budget boundary stops before loading the next body and retains its ID for the next page. Unknown, noncanonical, oversized or inconsistent rows fail closed with fixed errors; no raw binding, credential, source snapshot or digest is returned to the controller. Legacy participant-index version 0 is refused without guessed identities or automatic backfill. Existing legacy service paths are not changed by that discovery restriction.

Payload reads recheck header lengths, row version and participant identities against the original bounded binding. List records have no approval/execution eligibility. Detail reads plan all requester, executor, subject and approver identities, then reuse the native service's canonical account-lock ordering and current sysadmin/credential checks. Current People VIEW filtering supplies display names without profile-image loading; labels provide no authority.

## Commands and lifecycle

GET list, GET detail and the original-impact review do not approve or consume requests. All commands are POST with native CSRF validation. The new route uses the existing `previewCompoundApproval`, `approveApproval` and `executeApprovedCompound` methods; UI hints are neither a request binding nor an authorization source. The underlying methods reacquire their locks and revalidate original parameters, current roles and sources, expiry, executor and ledger.

Self-approval, nonexecutors, disabled/nonadmin actors, expiry and source changes are refused. Consumed records display no new action and new workbench POSTs refuse them. The existing executor-only idempotent ledger replay remains supported by the original service; it cannot create another membership/appointment or consume a second approval. No original mutation method or permission rule is replaced.

## Evidence gates

Host controls execute actual native value/projection/route methods and unchanged page/control-flow method bodies with explicitly named SQL/framework seams. They cover empty displayed pages with progress, all-row length checks before payload load, 1 MiB and 32-participant boundaries, original-body change refusal, canonical/deduplicated participant planning, view-only GETs and POST refusal paths. These controls do not authenticate a real user or prove database locks, native HTTP dispatch or browser behavior.

The independent `--organization-approval-workbench` CLI prepares real native users/sessions in an owned disposable full fixture and calls the actual service and controller. Its source-derived expected count is 26 (six bootstrap, seventeen component/controller obligations, three cleanup), not 26 SQL statements. It includes independent setup fingerprints of complete fixed-schema rows across the six relevant tables (all JSON lengths planned before body reads; 64 rows per table, 32 KiB per payload and 2 MiB total plan), real controller GET list and detail, exact original-impact dialog content/hidden fields, an independently proved approved state before the source-drift test, native proposal/independent approval/execution, self/CSRF/nonadmin/disabled/foreign-executor refusal, consumed route refusal plus original ledger replay, source drift, one owned audit-trigger rollback followed by normal execution, and an explicitly test-only expired-binding storage fault. The latter is not proof of waiting for wall-clock expiry. No new services, workers, auxiliary SQL connections or grants are required. The public consumer checks exact current source/PHP, all obligations, full restore metadata, typed zero-worker cleanup and all false completion/permit boundaries.

All new supported mapper, native pure, SQL/controller, real HTTP-server, browser, hosted CI and deployment acceptance remain unexecuted.
